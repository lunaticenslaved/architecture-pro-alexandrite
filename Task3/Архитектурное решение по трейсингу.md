# Архитектурное решение по трейсингу

## Места, где запрос может зависнут

- Shop API -> MES API
    - загрузка модели
    - расчёт стоимости заказа
- MES API -> RabbitMQ
    - публикация события о завершении расчета
- RabbitMQ -> CRM API
    - приём заказа
- MES API -> MES UI
    - назначение заказа оператору
- MES API -> MES DB
    - запись заказа и его статуса

## Данные для трейсинга

- trace_id - ID заказа-запроса.
- URL запроса.
- span_id - этап обработки (расчет, публикация, прием и т.д.).
- order_id - ID заказа.
- имя очереди для сообщений.
- service_name - имя сервиса.
- Время входа и выхода из этапа обработки.
- HTTP метод.
- routing key.
- код ответа или флаг ошибки.

## Мотивация

Начилие трейсинга позволит понимать:

- дошёл ли заказ до CRM и был ли зарегистрован
- где именно произошла потеря заказа
- на чььй стороне проблема в случае долгоро расчёта стоимости заказа

Кроме того будет улучшены следующие бизнес-метрики:

- Соблюдение SLA с партнёрами (заказ < 1 часа).
- Меньше ручных разборов и вызовов специалистов.
- Время реакции на жалобы — с суток до 10 минут.
- Сокращение MTTR (время восстановления после сбоя).
- Зависшие заказы → стремимся к нулю.

## Предлагаемое решение

- Внедрение OpenTelemetry в проекты
- Использование Jaeger

Требуется добавить новые элементы в инфрастуктуру. [Схема](./C4-container-tracing.drawio)

## Компромиссы

- RabbitMQ: контекст не передаётся автоматически — нужно вручную добавлять trace_id в заголовки. Дорого.
- OpenTelemetry в MES (C#): нет готовой автоматической настройки (в отличие от Java), потребуются ручные доработки. Затратно.
- Трейсинг для S3 не приоритетен, на отслеживание статусов заказов не влияет.

## Безопасность

- Jaeger UI — только внутри защищённого контура, вход через SSO.
- В трейсы не попадают логины, email, личные данные и прочая конфиденциальная информация.
- Доступ: DevOps, бэкенд-разработчики, служба поддержки.
