# Архитектурное решение по логированию

## Системы, в которых используется логирование

- **CRM API (Spring Boot)** — запускает заказ в производство.
- **MES API (C#)** — ключевой сервис расчёта стоимости, часто «виснет».
- **Shop API (Spring Boot)** — единая точка входа для всех заказов.
- **RabbitMQ** — интеграционная шина, через которую теряются сообщения.

## Примеры сообщений логирования

### INFO

- Пользователь {user_id} оформил заказ {order_id}.
- 3D-модель для заказа {order_id} загружена.
- Статус заказа {order_id} в системе {system} изменён с {old_status} на - {new_status}.
- Сообщение по заказу {order_id} отправлено в очередь {queue_name}.
- Сообщение по заказу {order_id} получено из очереди {queue_name}.

### Другие уровни логирования

- **FATAL** — сервис полностью неработоспособен.
- **ERROR** — исключения, сбой смены статуса, ошибка расчёта.
- **WARN** — некритичные сбои (например, повторная отправка в очередь).
- **DEBUG** — только для разработки (dev-среда), отладка логики.

## Мотивация для внедрения логгирования

### Причины для внедрения мониторинга

- **Быстрое расследование зависших заказов** — видно на каком шаге сбой (минуты вместо - часов).
- **Выявление долгих расчётов** — фильтрация аномалий для поиска сбоев в MES.
- **Контроль RabbitMQ** — видно, ушло сообщение и дошло ли до потребителя.
- **Сквозное отслеживание заказа** — полная картина пути заказа по всем сервисам.
- **Автообнаружение проблем** — алёрты по паттернам (например, рост ERROR).
- **Снижение нагрузки на поддержку** — поддержка сама видит причину без эскалации.
- **Аудит и безопасность** — кто, когда, что сделал с заказом.
- **Экономия на постмортемах** — готовая хронология инцидента.

### Улучшаемые бизнес-метрики

- **Процент зависших заказов** — стремится к 0% за счёт видимости каждого шага.
- **MTTR (время восстановления после сбоя)** — снижается с часов до минут.
- **Время реакции на жалобу клиента** — сокращается с суток до 10–15 минут.
- **Количество потерянных сообщений в RabbitMQ** — стремится к 0.
- **Доля инцидентов без привлечения разработчиков** — вырастает с 0% до 70% и выше (поддержка и DevOps работают по логам сами).

### Приоритетные сервисы

В силу ограниченного количества ресурсов определим приоритетные сервисы для внедрения логирования:

- **CRM API** - нужно отслеживать, запущен ли заказ в производство
- ***Rabbit MQ* - нужно проверять, не потерялись ли сообщения

## Предлагаемое решение

### Новые компоненты системы

| Компонент | Назначение | Где разворачивается |
|---|---|---|
| OpenSearch | Хранение, индексация и поиск логов (замена Elasticsearch) | Отдельные инстансы (кластер из 3 узлов для отказоустойчивости) |
| Filebeat | Лёгкий агент сбора логов с диска, отправка в Logstash | Каждый сервер с API (Java/C#) и RabbitMQ |
| Logstash | Централизованная обработка: парсинг, фильтрация, обогащение, маршрутизация | Отдельные инстансы (2+ для отказоустойчивости) |
| Kibana | Визуализация, поиск, дашборды, алёрты | Отдельный инстанс (за прокси с SSO) |

**Причина выбора стека:**
Бесплатная лицензия (OpenSearch vs платный Elastic), полная совместимость с экосистемой ELK, поддержка в любом облаке (on-prem тоже).

Требуется доработка инфраструктуры. [Схема](./C4-container-log.drawio)

### Политики безопасности

- **Сокрытие данных**:
    - Пароли, токены, email, телефон, ФИО, номера карт.
    - Замена чувствительных данных на [REDACTED] или guid на уровне приложения + фильтрация в Logstash

- **Ограничение доступа**:
    - DevOps / SRE — все логи (чтение, алёрты).
    - Бэкенд-разработчики — логи своих сервисов.
    - Поддержка — только по order_id/user_id, без sensitive полей.
    - Фронтенд, внешние пользователи — доступа нет.

- **Доступ через SSO**
    - Только SSO (Keycloak / AD) + MFA для DevOps.
    - Роли в OpenSearch Security Plugin.

- **Шифрование и аудит**
    - TLS при передаче, шифрование дисков и бэкапов.
    - Все действия в Kibana логируются в audit-индекс. Проверка — раз в месяц.

### Политики хранения

- **Именование**: logs-{service}-{YYYY.MM.DD} (shop, crm, mes, rabbitmq)
- **Размер**: ~5 ГБ/день суммарно, ~150 ГБ/месяц
- **Сроки**:
    - Production — 30 дней
    - Stage — 7 дней
    - Dev — 3 дня
- **Управление**: ILM в OpenSearch (hot → warm → delete)
- **Исключения**: аудит-логи — 1 год, снапшоты инцидентов в S3

## Алёртинг

### Какие алёрты настроить

- ERROR / FATAL — появление любой ошибки → тикет + вызов дежурного
- Отсутствие логов заказа > 10 минут → тикет + вызов дежурного
- Резкий рост заказов (>1000/мин) → тикет (DDoS / системный баг)
- Потеря сообщений в RabbitMQ (отправлено, но не получено >5 мин) → тикет

### Куда отправлять

- TaskManager (Jira/YouTrack) — единая очередь
- Telegram/Slack — для CRITICAL
- SMS / PagerDuty — только для CRITICAL (24/7)

### Режим тишины

- WARNING с 23:00 до 08:00 — только тикет, без звонков и сообщений.
- CRITICAL — доставляется всегда.

### Аномалии

| Аномалия | Пример | Что может означать |
|---|---|---|
| Резкий рост RPS | Было 4 заказа/сек → стало 10 000/сек | DDoS-атака, сломавшийся клиент, баг в ретраях |
| Рост ERROR без изменения кода	| Ошибки расчёта MES выросли с 0% до 15%	| Проблема с внешним сервисом (например, БД недоступна) |
| Заказы перестали создаваться | 0 новых заказов за 5 минут в час пик | Полный отказ Shop API или RabbitMQ |
| Рост времени обработки | Среднее время расчёта выросло с 200 мс до 30 секунд | Деградация БД, блокировки, утечка памяти |
| Аномальные паттерны в логах | Повтор одного и того же WARN 1000 раз за минуту	| Бесконечный ретрай, зацикливание |

## Выбор технологии

### Сравнение технологий

| Критерий | OpenSearch | ELK (Elastic) | Loki | Splunk |
|---|---|---|---|---|
| Лицензия | Apache 2.0 (бесплатно) | Elastic License + SSPL (ограничения для облаков) | AGPL (бесплатно) | Проприетарная (платная) |
| Стоимость | Бесплатно (поддержка — опционально) | Бесплатно для базовой версии (платно за enterprise) | Бесплатно | Очень дорого (по объёму данных) |
| Производительность | Высокая (полнотекстовый поиск) | Высокая (аналогично OpenSearch) | Средняя (оптимизирован под метаданные, не под текст) | Очень высокая |
| Поиск по JSON	| Отлично (native support) | Отлично | Частично (лучше с плагинами) | Отлично |
| RBAC / Безопасность | Встроенный Security Plugin | Платный (в Gold/Platinum) | Через reverse proxy + SSO (вручную) | Встроенный, гибкий |
| UI (визуализация) | Kibana (fork) — полнофункциональный | Kibana — эталон | Grafana — удобно, но менее мощный | Свой, мощный, но сложный |
| Алёртинг | Встроенный | Платный (в enterprise) | Через Grafana Alerting | Встроенный |
| Поддержка стеков (Filebeat, Logstash) | Полная (совместимость) | Родная | Ограниченная (промтейловый подход) | Свои агенты (тяжелее) |

### Обоснование выбора: OpenSearch

#### Плюсы

| Плюс | Пояснение |
|---|---|
| Бесплатная лицензия Apache 2.0 | Никаких рисков для бизнеса, можно использовать в любых проектах, включая коммерческие облака. |
| Полная совместимость с ELK | Используем существующие Filebeat и Logstash (ничего не переписываем). |
| Встроенный Security Plugin | RBAC, аудит, шифрование — всё из коробки без доплат. |
| Встроенный алёртинг и Anomaly Detection | Не нужно покупать отдельные решения для DDoS-детекции. |
| Отличная производительность | Индексация и поиск такие же, как у Elastic (до выхода Elastic 8.0+). |
| Активное сообщество | AWS развивает, документация и решения проблем доступны. |

#### Минусы

| Минус | Пояснение | Компенсация |
|---|---|---|
| Отставание от Elastic по новым фичам | Elastic 8.x имеет некоторые улучшения (например, в поиске по векторным полям) | Нам не нужны новейшие фичи, базовый поиск работает отлично |
| Меньше облачных managed-решений | У Elastic есть Elastic Cloud, у OpenSearch — только AWS OpenSearch Service | Используем self-managed или AWS OpenSearch Service |
| Меньше интеграций с SaaS | Некоторые инструменты (например, Datadog) лучше работают с Elastic | Наш стек (Filebeat + Logstash) полностью совместим |
| Документация иногда устаревает | Форк Elastic — некоторые примеры не обновлены | Сообщество и практика решают |

#### Почему не другие технологии

| Технология | Почему не подходит |
|---|---|
| ELK (Elastic) | Платная лицензия для Security и Alerting. |
| Loki | Слабый полнотекстовый поиск по JSON-логам, не подходит для глубокого анализа по order_id. Хорош для метрик, но не для логов заказов. |
| Splunk | Очень дорого при объёме ~5 ГБ/день. Выбор только при неограниченном бюджете. |
