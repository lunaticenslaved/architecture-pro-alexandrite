# Планирование: анализ, идентификация проблем и поиск решений

## Выявленные проблемы

- Низкая наблюдаемости системы. Проблема выявляется только если реальные пользователи сообщат о ней, сложности с дебагом системы.
- Отсутствие кэширования. Повышенная нагрузка на сервисы ухудшает их работу.
- Низкая отказоустойчивость системы. По одному экземляру кадого сервиса и БД недостаточны для продолжения работы системы, если один экземпляр выйдет из строя.
- Отсутствие репликации БД. Чтение и запись в единственную ноду (мастер) перегружают БД.
- Доступ к внутреннему контуру сервисов напрямую, а не через демилитаризованную зону. Это создаёт повышенные риск нарушения работы системы из-за DDoS-атак.
- Ручной CI/CD без релизов.
- Долгий расчёт стоимости заказа. Возможно, он выполняется синхронно и блокирует MES-сервер.
- Возможно, имеется потеря сообщений из RabbitMQ. Это бы объяснило проблему невыполнения заказов клиентов (CRM -> MES), но в отсутствии мониторинга сложно сказать, действительно имеется ли эта проблема.
- Нарушение разделения доменов. Информация о заказах должна храниться в CRM контуре, расчёт цены должен производиться в CRM контуре.

## Предлагаемые решения

| Решение | Комментарий | Приоритет |
|---|---|---|
| Внедрение мониторинга | Prometheus/Grafana | Высокий |
| Внедрение логирования | ELK | Высокий |
| Внедрение трейсинга | OpenTelemetry + Jaeger | Высокий |
| Внедрение кэширования | Redis. Паттерны Read-Through и Write-Through | Высокий |
| Вынесение расчёта стоимости заказов в отдельный сервис в CRM-контуре | Сервис должен взаимодействовать с остальной системой асинхронно. Это разгрузит MES-сервер | Высокий |
| Вынесение менеджмента заказов в CRM-контур | Это позволит лучше разделить доменные области | Высокий |
| Внедрить горизонтальное масштабирование сервисов | Минимум 3 пода каждого сервиса в проде. Это может потребовать изменения кода приложения для устранения логики, которая будет запускаться на каждом поде | Средний |
| Внедрить репликации БД | Минимум 3 реплики, одна из которых мастер. Это может потребовать изменения кода приложения для явного указания чтения из реплик. | Средний |
| Выделить внешнее API в изолированный контур | - | Средний |
| Повысить наблюдаемость RabbitMQ, внедрить ретрай сообщений | С тестированием, релизами и возможностью отката релиза | Низкий |
| Внедрить CI/CD | С тестированием, релизами и возможностью отката релиза | Низкий |


## DOD к концу срока в 6 месяцев

### Целевая архитектура

По прошествии 6 месяцев архитектура компании должна приобрести вид, указанный на [схеме](./C4-container-target.drawio). Новые контейнеры выделены зелёным цветом.

Примечания:

1. Появляется отдельное публичное API, которое доступно для внешних пользователей. Через него можно создать заказы и посмотреть статусы и цены по этим заказам. 
2. Вся информация по заказам, включая их статусы, хранится только в CRM. CRM становится ядром всей системы, поэтому нужно повысить её надёжность внедрением кэширования.
3. Функционал расчёта цены выводится из MES-контура и заводится в CRM-контур как отдельный сервис. Этот сервис получает уведомления через очередь сообщений о небходимости расчёта стоимости заказа и так же через очередь сообщений уведомляет CRM API о завершении расчётов.
4. MES становится полностью изолированной внутренней системой, которая связана с CRM асинхронно через очередь сообщений.

### Задачи

1. Повышение наблюдательности системы.
    - Определить необходимый набор метрик.
    - Развернуть инфраструктуру для сбора данных.
    - Настроить сервисы для просмотра метрик и трейсов.
    - Настроить сбор метрик с инфраструктуры.
    - Настроить логирование приложений.
2. Внедрение кэширования для MES API.
    - Развернуть инфраструктуру.
    - Дополнить код приложений для использования кэша.
3. Вынесение расчёта стоимости заказов в отдельный сервис.
    - Развернуть инфраструктуру Price Calculator API.
    - Вынести код из MES-системы в Price Calculator API, покрыть тестами.
    - Завязать Price Calculator API на получение задач на расчёт из очереди сообщений.
    - Поддержать в Price Calculator API отправку сообщений о завершении отчёта в очередь сообщений.
    - Поддержать в Site API обновление заказа по сообщениям из Price Calculator API.
    - Поддержать в MES API обновление заказа по сообщениям из Price Calculator API.

--- На этом моменте нагрузка на MES API должна значительно снизится ---
4. Настроить горизонтальное масштабирование сервисов.
5. Настроить репликации БД.
6. Вынесение публичного API в Public API Service.
    - Развернуть инфраструктуру Public API Service.
    - Написать код сервиса, который по сути представляет собой прокси к внутренним сервисам.
    Примечание: в будущем, если при текущей схеме будет повышенная нагрузка на CRM, то можно расширить функционал публичного сервиса, добавив сюда кэширование или дополнительную в БД, которая будет заполняться данными, которые нужны партнёрам, по сообщения из Message Queue. 
7. Вынести управление заказами из Site API в CRM API.
    - Добавить базу данных в CRM контур.
    - Вынести API управления заказами из Site API.
    - Настроить кэширование в CRM контуре.
    - Поэтапная миграция данных из Site API. Поддержать одновременную запись заказов в Site API и CRM API.
    - Переключить публичное API на чтение из CRM.
    - Удаление неактуального кода из Site API.
8. Повысить наблюдаемость RabbitMQ, внедрить ретрай сообщений.
9. Внедрить CI/CD.

### Минимальный список задач в условиях ограниченных ресурсов

1. Повышение наблюдательности системы.
    - Обосноание: это посысит наблюдаемость системы, что позволит, во-первых, более точно локализовать текущую проблему; во-вторых, позволит оперативно реагировать на возникающие проблемы при дальнейшей доработке системы.
2. Внедрение кэширования для MES API. 
    - Обоснование: в целевой архитектуре не предполагается использование кэша для MES, но в текущей реализации использование кэша позволит снять часть нагрузки с проблемного сервиса. В дальнейшем кэш можно сохранить, но, кажется, что при достижении целевой архитектуры необходимости в кэше не будет. Впрочем, выводы относительно этого лучше делать уже по факту на основани мониторинга.
3. Вынесение расчёта стоимости заказов в отдельный сервис. 
    - Обоснование: решение этой задачи приблизит систему к целевой архитектуре и разгрузит MES API.
